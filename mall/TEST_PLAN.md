# Mall-X 多商家电商平台 · 综合测试方案（基准文档）

> 版本：v1.0 ｜ 适用范围：mall 全部微服务与前端 ｜ 维护：随每次发布迭代更新
> 目标：作为质量保障（QA）基准，指导功能完整性、性能与稳定性验证，保证测试**可操作、可重复、可扩展**。

## 一、被测系统与测试范围

### 1.1 系统架构

| 组件 | 说明 | 端口 |
| --- | --- | --- |
| mall-gateway | 统一入口、路由、Redis+Lua 限流、Sentinel 熔断 | 10010 |
| mall-mgr | 商户/商品/订单/退款售后/资金/统计/平台管理 | 10020 |
| mall-alipay | 统一支付下单、渠道对接、回调幂等 | 10030 |
| mall-vue | 用户商城 + 商户后台 + 平台后台（Vue3+TS） | 5173 |
| 中间件 | MySQL(3307) / Redis / Nacos / RocketMQ | docker |

### 1.2 核心业务链路（必须全绿）

```
商户注册(验证码) → 平台审核 → 发布商品 → 用户浏览/加购 → 下单(Lua扣库存)
→ 支付下单 → 渠道回调(幂等) → MQ驱动订单待发货 → 商户发货 → 用户确认收货
→ 退款售后(申请/凭证/四态审核/双端同步) → 资金结算 → 提现审核 → 统计报表
```

| --- | --- | --- | --- |

## 二、测试环境与数据准备

### 2.1 环境要求

| 项 | 配置要求 |
| --- | --- |
| 硬件 | ≥ 4C8G（压测环境建议 8C16G 独立宿主，避免与开发共用） |
| 操作系统 | Windows 10/11（当前基线）或 Linux（压测推荐） |
| 运行时 | JDK 21 / Node 24 / Python 3.11+（playwright、requests） / Docker Desktop |
| 中间件 | MySQL 8.x（独立数据卷）、Redis 7.x、RocketMQ 5.x、Nacos 2.x |
| 浏览器 | Chromium(Playwright 内置) + Chrome/Edge 最新稳定版（手工兼容性补充） |

### 2.2 环境分层

| 环境 | 用途 | 数据策略 |
| --- | --- | --- |
| E0 mock | 前端独立开发自测（`VITE_USE_MOCK=true`） | 内存种子，刷新即重置 |
| E1 联调 | 功能/集成/E2E（真实后端，MySQL 3307） | 种子 SQL + 演示数据（`demoData.sql`，近 7 天动态生成） |
| E2 压测 | 性能/稳定性 | **独立数据卷**，压测前重置基线，禁用演示数据干扰 |

### 2.3 测试数据准备方式

| 数据类别 | 准备方式 | 要求 |
| --- | --- | --- |
| 基线种子 | `sql/mallDb.sql → mallTable.sql → mallInsert.sql → demoData.sql` 按序导入 | 每轮测试前重置；含演示账号（admin/shop1/shop2/user1/user2）与近 7 天交易 |
| 动态数据 | E2E 脚本自带**随机后缀自洽账号**（新商户/新用户/新商品闭环），互不污染 | 可重复执行，不依赖固定数据 |
| 参数化数据 | API 测试用例内联生成（随机手机号、随机后缀） | 避免唯一键冲突 |
| 清理与回滚 | 清理前 `mysqldump` 备份至 `sql/backup/`；按编号定位段（如 `9000000000`）删除演示数据；测试残留按「非种子/非演示」规则事务清理 | 清理后必须接口冒烟验证 |
| Redis 基线 | 种子商品库存 key 与 DB 一致；测试后删除非种子 key | 缓存与库一致性属验证点 |

## 五、边界条件与异常处理用例

| 类别 | 用例设计思路 | 关键验证点 | 预期结果 |
| --- | --- | --- | --- |
| 参数校验 | 缺参/空串/null/类型错误（字符串传数字字段） | @Valid 校验与全局异常处理器 | 统一 `id≠0` 业务错误，**不 500** |
| 金额精度 | 0.01/0.005/超大额(12,位)/负数 | DECIMAL 精度与 @DecimalMin | 拒绝非法值，合法值无精度丢失 |
| 长度边界 | 恰好 255 字符、超长文本、emoji、纯空格 | 列宽与校验 | 拒绝或安全截断，不破坏布局 |
| 分页边界 | pageNum=0/负数/超大、pageSize 极大值 | 分页插件 | 返回空页或修正值，不异常 |
| 组合状态 | 对已关闭订单发货/对已退款单再退款/对待支付单售后 | 状态机条件更新 | 一律拒绝并提示当前状态 |
| 资源不存在 | 随机不存在的单号查询/删除 | 查询与删除路径 | 统一「不存在或已被删除」 |
| 文件上传 | 非图片后缀/超 5MB/伪造扩展名 | 类型与大小双重校验 | 拒绝 |
| 中文与编码 | 中文商品名/地址全链路（含导出、日志、图片文件名） | utf8mb4 全链路 | 无乱码（上传目录中文路径已用原生 Path 方案规避） |

## 六、并发、性能与稳定性

### 6.1 并发场景清单

| 场景 | 注入方式 | 关键验证点 | 预期结果 |
| --- | --- | --- | --- |
| 库存超卖 | N 线程并发下单同一商品（N>库存） | 成功单数=库存、DB 与 Redis 一致 | 零超卖 |
| 回调竞态 | 同一支付单并发回调多次 | 唯一索引+锁 | 仅一次副作用 |
| 退款审核竞态 | 商户端与平台端同时审核同一退款单 | Redisson 锁 | 仅一次生效 |
| 重复提交 | 双击提交订单/退款 | 前端防抖+后端幂等 | 不产生重复单 |
| 限流触发 | 400 并发（30 线程）✔ | 全局 1000 QPS/IP 200 QPS | 超限统一文案，服务不崩 |

### 6.2 性能测试方案

| 项 | 内容 |
| --- | --- |
| 指标基线 | 网关层 QPS ≥ 1000；读接口 P99 ≤ 500ms、写接口 P99 ≤ 800ms；错误率 < 0.1% |
| 场景 | ① 商品列表读 ② 商品详情(缓存命中/未命中) ③ 下单写（含库存）④ 统计聚合 ⑤ 混合场景（读:写=8:2） |
| 加压模型 | 阶梯加压 100→500→1000→1500 并发，每级持续 5min，观察拐点 |
| 稳定性 | 1000 QPS 持续 8h：观察内存泄漏（JVM 堆）、连接池耗尽、Redis/MQ 积压、日志异常增长 |
| 资源监控 | 宿主 CPU/内存/IO、JVM（堆/GC/线程）、MySQL（慢查询/连接数）、Redis（命中率/内存）、MQ（积压） |
| 环境 | E2 独立压测环境；压测前重置数据基线；压测账号与数据打标（如 `PERF` 前缀）便于清理 |
| 通过标准 | 达到指标基线且无级联失败；未达标需输出瓶颈分析（慢 SQL/锁竞争/GC）与优化结论 |

| 必填要素 | 环境(E0/E1/E2)、账号与数据（单号等可复现标识）、复现步骤、期望 vs 实际、证据（截图/日志片段/接口报文） |
| 附件留存 | E2E 截图目录 `test-results/`、服务日志 `logs-test/`、接口响应 JSON |
| 状态流转 | 新建 → 确认 → 修复中 → 待验证（关联回归用例）→ 关闭；拒绝需注明理由 |

## 九、回归测试策略

| 触发时机 | 回归范围 |
| --- | --- |
| 缺陷修复后 | 该模块全部用例 + 冒烟集（e2e_page_smoke） |
| 每次代码合入（每日） | `api_test.py` 全量 + `e2e_page_smoke` |
| 发布前 | 全量：api_test + 四套 E2E + 性能冒烟（限流/库存并发） |
| 依赖/配置变更（中间件升级、费率/渠道配置） | 受影响模块全量 + 幂等与状态机专项 |
| 数据修复/清理后 | 接口冒烟（登录/列表/统计）确认基线完好 |

> 原则：**修复必须带回归用例**——每个 P0/P1 缺陷关闭前，需在自动化脚本中补一条对应用例，防退化。
