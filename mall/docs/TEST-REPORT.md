- 防篡改：无签名 / 伪造签名 / 写操作缺签名 全部拒绝
- 验证码安全：一次性消费（**防重放**）、错误码拒绝
- 输入校验：超长用户名(60) / 弱密码(1位) / 非法字符用户名 / 超长密码(50) / 超长店铺名(200，防 DB 列溢出 500) / 非法手机号 —— 全部 400 友好拒绝
- 异常处理：不存在商品/审核单/支付单/商户 → 业务错误而非 500 崩溃
- 注入防护：SQL 注入登录失败、XSS 载荷仅作查询条件、非法分页/超大 pageSize 不崩溃

## 五、问题列表

### 1. 【高·已修复】JWT 令牌校验必然失败（时间戳单位错误）
- **现象**：`JwtUtil.verify()` 对任何由本系统签发的令牌均返回 `null`（单元测试首轮 3 项失败）。
- **定位**：调试测试输出 `verify=true`（签名正确）但 `validate=false`。根因是 `create()` 用 **毫秒** 写入 `iat`/`exp`，而 hutool `JWT.validate()` 按**秒**判定 → `iat` 被视为"未来签发" → 校验失败。
- **影响**：令牌校验链路完全不可用。当前业务仅签发不校验（token 交前端保存），故为**潜在缺陷**；但 README 声称 JWT 鉴权，后续扩展鉴权将直接踩坑。
- **修复**：`JwtUtil` 改用秒级时间戳（`TTL_SECONDS = 7*24*3600`），并新增 2 条回归用例锁定该行为。

### 2. 【低·用例修正】单号"单调递增"假设不成立
- `OrderNoUtil` 单号含 5 位随机段（防遍历），本就不保证严格递增 → 原用例假设错误，已改为格式校验（前缀 + 17 位时间戳 + 9 位数字段，长度 28 固定）。

### 3. 【中·观察】400 并发下 97 次非限流失败
- 400 请求中：成功 48、限流 255、**其他失败 97**（既非成功也非"系统繁忙"）。
- 推测为客户端侧因素（Python `urllib` 无连接池 + 60 线程瞬时建连），或网关连接队列拒绝。
- **建议**：用专业压测工具（JMeter / wrk / k6）复测以区分客户端与服务端因素；服务端可评估 Netty 连接队列参数。

### 4. 【低·优化】Nacos CPU/内存偏高
- Nacos 容器 CPU 45.5%、内存 883 MB（compose 配置 `JVM_XMS=256m/JVM_XMX=512m` 未生效于实际占用）。
- **建议**：调整 Nacos 启动参数；生产环境建议关闭其内置 Derby 并使用外置存储。

### 5. 【低·建议】补充单元测试覆盖
- 当前单测集中在 `mall-common` 工具类；`mall-mgr` 业务层（订单/退款/资金状态机与幂等逻辑）依赖集成测试覆盖，建议后续补充可控 mock 的单元测试（如退款可退余额校验、状态机流转）。
